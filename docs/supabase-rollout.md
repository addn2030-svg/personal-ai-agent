# 🚦 خطة التشغيل التدريجي والتراجع (Zero-Downtime)

كيف تُدخل طبقة Supabase إلى نظام يعمل بالفعل — بلا توقف، وبأدلة، وبتراجع فوري.

## الفكرة في سطر واحد

**سير العمل القديم لا يُلمَس في أي مرحلة.** لا مرحلة تُطفئ شيئًا من النظام القائم، ولا
تُلغي مصدر الحقيقة، ولا توقف حلقة المدير. الذي يتغيّر تدريجيًا هو **مقدار ما تفعله
الطبقة الجديدة تلقائيًا** — لا أكثر.

```
state.json ──sync──▶ tasks_mirror     ← الطبقة الجديدة (مشتقة)
     ▲
     └── يبقى مصدر الحقيقة الوحيد، وكل الأنظمة القديمة تعمل عليه كما هي
```

## المراحل الخمس

| المرحلة | ما تُفعّله الطبقة الجديدة | أثرها على القديم | التراجع |
|---|---|---|---|
| **0 · dormant** | لا شيء — ولا اتصال شبكة | صفر | — |
| **1 · shadow** | قراءة ومقارنة آلية (`reconcile`) | صفر | `kill` |
| **2 · canary** | كتابة بأمر بشري صريح فقط | صفر | `kill` |
| **3 · dual** | الدفعة اليومية التلقائية | صفر — تعمل بالتوازي | `rollback --to canary` |
| **4 · primary** | النسخ التلقائي هو المسار الافتراضي | الخطوة اليدوية المتوارثة تصبح اختيارية (لا تُحذف) | `rollback --to dual` |

```bash
python3 -m engine.rollout status      # أين نحن الآن؟ وما الذي ينقص للترقية؟
python3 -m engine.rollout plan        # جدول المراحل وما لن يُلغى أبدًا
python3 -m engine.rollout simulate    # محاكاة بلا أي تغيير
```

## قاعدتان تحكمان التصميم

**1) الأتمتة مقيَّدة بالمرحلة؛ الإنسان لا يُمنع أبدًا.**
الأوامر الصريحة (`push` · `sync` · `reconcile` · `restore` · `/backup_now`) تعمل في **كل**
المراحل — حتى `dormant`. السبب مقصود: لو انكسر شيء، يجب أن يبقى باستطاعتك أخذ نسخة
احتياطية الآن. حجب النسخ خلف راية إعداد خطأ أخطر من الخطأ نفسه.

**2) الفشل ينغلق على الأأمن.**
ملف المرحلة تالف أو مفقود أو غير مفهوم ⇒ تُقرأ `dormant` ⇒ يتوقف كل شيء تلقائيًا.
وأي عطل في تقييم المرحلة **لا يتسرب كاستثناء إلى حلقة المدير** — يُطفئ الأتمتة فقط.

## المسار العملي — خطوة بخطوة

### الخطوة 0 — التثبيت بلا أي أثر

```bash
# لا تضع أي متغير بعد. المرحلة الافتراضية dormant بلا إعداد.
python3 -m engine.rollout status     # يجب أن ترى: 0 · خاملة
```

علامة النجاح: النظام يعمل كما كان تمامًا، و`audit.jsonl` لا يحتوي أي حدث Supabase.

### الخطوة 1 — الظلّ (قراءة بلا كتابة)

```bash
# أضف في البيئة: SUPABASE_URL + SUPABASE_ANON_KEY (المفتاح العام يكفي للقراءة)
python3 -m engine.rollout advance             # ⇒ shadow (بعد أدلة كافية)
python3 -m engine.rollout reconcile           # دليل: يقرأ ويقارن ولا يكتب
```

في هذه المرحلة **لا تُكتب أي بيانات في Supabase**، ومع ذلك نعرف يقينًا أن الاتصال
والمفاتيح والجداول والمخطط تعمل. تكرار `reconcile` يبني الأدلة للترقية التالية.

### الخطوة 2 — التجريبية (كتابة بأمر بشري)

```bash
# أضف: SUPABASE_SERVICE_ROLE_KEY + SUPABASE_WRITE_ENABLED=1
python3 -m engine.rollout advance             # ⇒ canary
python3 -m connectors.supabase_state push --reason "أول نسخة حقيقية"
python3 -m connectors.supabase_tasks sync
python3 -m engine.rollout reconcile           # القاضي: هل المرآة تطابق الحالة؟
```

الأتمتة **ما تزال مطفأة**: لا شيء يحدث إلا حين تكتب الأمر بيدك.

### الخطوة 3 — المتوازية (التلقائي يعمل، والقديم كما هو)

```bash
# أضف: SUPABASE_BACKUP_SCHEDULE_ENABLED=1
python3 -m engine.rollout advance             # ⇒ dual
```

من هنا تعمل دفعة يومية واحدة (نسخة كاملة + مزامنة المرآة) داخل حلقة المدير.
**كل شيء قديم يعمل كما هو بالتوازي**: `/brief` · `/tasks` · الاستباقية · الجدولة · بوابة
الاعتماد. راقب عدة أيام:

```bash
grep supabase audit.jsonl | tail -20          # نجاح؟ أخطاء؟
python3 -m engine.rollout reconcile           # انحراف صفري مستمر؟
```

### الخطوة 4 — الأساسية (بعد التحقق الكامل)

```bash
export SUPABASE_PRIMARY_ACK=I_VERIFY_SUPABASE_LAYER_IS_STABLE
python3 -m engine.rollout advance --reason "استقرار مؤكد 5 أيام"
```

المرحلة الأخيرة **لا تُفرض بـ`--force`** — تحتاج البوابة والتوقيع معًا. وهنا فقط:

- يصبح النسخ التلقائي هو المسار المعتاد، ويصير `/backup_now` اليدوي اختياريًا.
- **لا يُحذف أي أمر قديم**، ولا تتوقف أي طبقة.

## التراجع — بلا شروط وبلا انتظار

```bash
python3 -m engine.rollout kill                    # إيقاف فوري ⇒ dormant
python3 -m engine.rollout rollback --to canary --reason "انحراف متكرر"
```

أو من الجوال مباشرة: **`/rollout_kill`**.

ما يحدث عند التراجع: تتوقف الأتمتة الجديدة **فقط**. لا يُحذف صف، ولا نسخة، ولا يتغير
`state.json`. كل الأنظمة القديمة لم تكن متوقفة أصلًا، فلا شيء يُعاد تشغيله.

> لماذا لا يُكتب التراجع من تيليجرام كخطوة للأمام؟ لأن **إجراءات تقليل المخاطر**
> (الإيقاف) يجب أن تكون أسهل من أي شيء آخر — متاحة من الجوال بضغطة. أما **إجراءات رفع
> المخاطر** (الترقية) فتبقى في الطرفية: تحتاج مراجعة أدلة وجلسة متعمَّدة.

## شروط الترقية (البوابة بالأدلة لا بالنيّة)

| الخطوة | الشرط | لماذا |
|---|---|---|
| → shadow | تشغيلان ناجحان موثّقان | نتحقق أن أداة المقارنة تعمل |
| → canary | تشغيلان ناجحان موثّقان | نفس الشرط |
| → dual | 3 تشغيلات + **آخر مقارنة بانحراف صفري** + صفر أخطاء | الكتابة اليدوية أثبتت التطابق |
| → primary | 5 تشغيلات + انحراف صفري + صفر أخطاء + **توقيع حرفي** | القرار الأخير بشري |

الأدلة تُقرأ من `audit.jsonl` **داخل نافذة المرحلة الحالية فقط** — فنجاح قديم من مرحلة
سابقة لا يُحتسب.

> **ملاحظة تصميمية مهمة:** لا يُشترط «انحراف صفري» في الظلّ. الظلّ لا يكتب، فاشتراط صفره
> يعني حلقة مفرغة: لا نكتب حتى نتأكد، ولا نتأكد حتى نكتب. لذلك يُشترط الانحراف الصفري
> عند خطوة `dual` فقط — بعد أن تكون الكتابة قد بدأت فعلًا. (اكتُشف هذا الخلل باختبار
> حقيقي على الخادم المحلي، لا بالمراجعة النظرية.)

**الحدود الدنيا في الكود لا في البيئة:** متغيرات البيئة **ترفع** المتطلبات ولا تخفضها
أبدًا — فلا خطأ إعداد يفتح ترقية بلا أدلة.

## ما لن يُلغى في أي مرحلة

1. `data/state.json` يبقى مصدر الحقيقة الوحيد — لا يصبح Supabase مرجعًا.
2. بوابة الاعتماد `action_queue` وكل ما يمر بها (لا أثر خارجي بلا اعتماد).
3. حلقة المدير `manager --loop` تعمل بلا توقف في كل المراحل.
4. أوامر الطوارئ اليدوية تبقى متاحة: `push` · `restore` · `stats` · `/backup_now`.
5. لا حذف لأي بيانات عند التراجع — النسخ تبقى؛ التراجع لا يمحو أثرًا.

هذه القائمة مُختبَرة آليًا (`tests/test_rollout.py`)، فليست وعدًا شفهيًا.

## صمامات الأمان المزدوجة

الأتمتة تحتاج **شرطين مستقلين** معًا — خطأ إعداد في أحدهما لا يكفي وحده:

| ما نريد تشغيله | الشرط الأول | الشرط الثاني |
|---|---|---|
| الدفعة اليومية | المرحلة ≥ `dual` | `SUPABASE_BACKUP_SCHEDULE_ENABLED=1` |
| أي كتابة | `SUPABASE_SERVICE_ROLE_KEY` سري | `SUPABASE_WRITE_ENABLED=1` |
| المرحلة الأخيرة | اجتياز البوابة | `SUPABASE_PRIMARY_ACK` |

## قائمة تحقق قبل الترقية (نسخ/لصق)

```bash
python3 -m engine.rollout status          # ما ينقص؟
python3 -m engine.rollout simulate        # ماذا سيتغير؟ (يجب أن ترى: صفر على القديم)
python3 -m engine.rollout gate            # الأدلة
bash scripts/verify_supabase.sh           # كل الفحوص خضراء
python3 -m engine.rollout advance         # خطوة واحدة فقط
```

وبعد كل ترقية: `python3 /engine/rollout.py status` ثم راقب `audit.jsonl` يومًا كاملًا قبل
الخطوة التالية. **الخطوة الأخيرة تحتاج استقرارًا مؤكدًا لعدة أيام، لا ساعات.**

## للطوارئ

| الحالة | الإجراء |
|---|---|
| أي خطأ متكرر في الطبقة الجديدة | `/rollout_kill` من الجوال |
| انحراف بين المرآة والحالة | `kill` ثم `reconcile` لتصنيف الفرق |
| فقدان بيانات محلية | `supabase_state restore --id N --apply` (يعمل في أي مرحلة) |
| مشروع Supabase موقوف (خطة مجانية) | الطبقة تتوقف، والنظام يستمر على `state.json` — استعد المشروع ثم `advance` |
| تلف ملف المرحلة | يقرأها النظام `dormant` تلقائيًا — لا يتعطل شيء |
