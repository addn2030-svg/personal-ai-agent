# Abdulrahman AI OS v0.4

نظام تشغيل شخصي بالذكاء الاصطناعي: وكيل رئيسي (Chief of Staff) + 6 مهارات، يقرأ من **مخزن حالة موحد** ويخرج بريفًا يوميًا ومراجعة أسبوعية وكشف أنماط، وكل إجراء خارجي يمر بـ**طابور اعتماد** مرتبط ببصمة المحتوى.

## الجديد — 🚦 التشغيل التدريجي والتراجع (نشر بلا توقف)
- **القاعدة**: الطبقة الجديدة تُشغَّل **بالتوازي** مع سير العمل القائم، ولا يُغيَّر أو يُوقف
  أي شيء قديم حتى تُثبت الطبقة الجديدة نفسها **بالأدلة** — لا بالنيّة.
- **خمس مراحل لا تُقفز**: `dormant` (لا شيء) → `shadow` (قراءة ومقارنة فقط، صفر كتابة)
  → `canary` (كتابة بأمر بشري فقط) → `dual` (أتمتة تعمل والقديم يعمل كما هو)
  → `primary` (النسخ التلقائي هو الافتراضي — والخطوة اليدوية تصبح اختيارية لا محذوفة).
- **البوابة بالأدلة**: كل ترقية تحتاج عدد تشغيلات ناجحة موثّقة + **آخر مقارنة بانحراف
  صفري** + صفر أخطاء (والخطوة الأخيرة تحتاج **توقيعًا بشريًا حرفيًا**). والحدود الدنيا في
  الكود لا في البيئة — متغيرات البيئة ترفع المتطلبات ولا تخفضها.
- **التراجع متاح دائمًا وفوري وبلا شروط**: `python3 -m engine.rollout kill` أو
  **`/rollout_kill` من الجوال**. التراجع **لا يمحو شيئًا**: لا صف ولا نسخة ولا يمسّ
  `state.json` — تتوقف الأتمتة الجديدة فقط.
- **الأتمتة مقيَّدة؛ الإنسان لا يُمنع**: أوامر النسخ والاستعادة تعمل في كل المراحل
  (حتى `dormant`) — فلا يُحبس المالك خلف راية إعداد وقت الحاجة.
- **الفشل ينغلق على الأأمن**: ملف المرحلة تالف/مفقود ⇒ `dormant` تلقائيًا، وأي عطل في
  تقييم المرحلة **لا يتسرب كاستثناء إلى حلقة المدير**.
- **صمامات مزدوجة**: الدفعة اليومية تحتاج المرحلة ≥ `dual` **و**
  `SUPABASE_BACKUP_SCHEDULE_ENABLED=1` — خطأ إعداد في أحدهما لا يكفي وحده.
- `python3 -m engine.rollout status|plan|simulate|gate|reconcile|advance|rollback|kill`
  · الخطة الكاملة وقائمة «ما لن يُلغى أبدًا»: `docs/supabase-rollout.md`
  · الاختبارات: `tests/test_rollout.py` (51) + 7 سيناريوهات تدريجية في اختبار E2E.

## الجديد — 🪞 مرآة المهام (استعلام مهامك بـSQL ومن الجوال)
- **ماذا تضيف**: جدول `tasks_mirror` في Supabase يعكس قسم `tasks` من حالتك، فتستعلم عن
  مهامك بـSQL أو من **Table Editor على جوالك** بلا لمس منطق النظام.
- **الاتجاه واحد**: `state.json ──sync──▶ tasks_mirror`. مصدر الحقيقة يبقى الحالة وحدها
  (عليها بوابة الاعتماد والاستباقية والتدقيق)، فلا «حجز مزدوج» ولا مهمة تُغلق في مكان
  وتبقى مفتوحة في آخر. الجدول قابل لإعادة البناء كاملًا في أي وقت.
- **idempotent**: معرّف كل صف حتمي من (العنوان + الموعد + المصدر + رقم التكرار)، فإعادة
  المزامنة لا تكرّر صفًا، وإغلاق مهمة يُحدّث صفّها نفسه. وكل صف يحمل بصمة آخر دورة
  (`sync_run`) — أي صف لا يحملها **يُحذف** تلقائيًا فلا بقايا يتيمة.
- **حقول مشتقة تختصر عليك الاستعلام**: `status_norm` يوحّد مفرداتك العربية والإنجليزية
  («منجزة»/«مكتملة»/`done` → `done`) و`is_open`/`is_overdue` محسوبتان مسبقًا. وما لا
  تفهمه حالةٌ مجهولة لا «لم تبدأ» — لا نخمّن حالة مهمة.
- **حماية صريحة**: لا «سياسات متساهلة» كما في الأدلة الجاهزة (سياسة متساهلة + مفتاح عام =
  قائمة مهامك الشخصية مكشوفة). هنا RLS مفعّل، ولا سياسة واحدة، والمفتاح العام لا يقرأ صفًا.
  وعرض القراءة `tasks_dashboard` يستبعد `notes` عن قصد (قد تحمل تفاصيل صحية).
- **أمان ضد أخطر خطأ**: لو تعذّرت قراءة الحالة (تشغيل أول · مسار خاطئ · ملف مقطوع)
  **يرفض الموصل المزامنة ولا يحذف شيئًا** — «لا مهام» ≠ «لا أستطيع القراءة».
- **الاستخدام**: `/tasks_stats` من الجوال (متأخرة · اليوم · بلا موعد) ·
  `python3 -m connectors.supabase_tasks stats|sync|sql` · SQL في `supabase/02_tasks_mirror.sql`
  · والدفعة اليومية تلقائية عند `SUPABASE_BACKUP_SCHEDULE_ENABLED=1`.

## الجديد — ☁️ نسخ الحالة إلى Supabase (طبقة متانة خارج الخادم)
- **المشكلة التي يحلّها**: مصدر الحقيقة `data/state.json` يعيش على قرص Railway وحده،
  والنسخ الدوارة على **نفس** القرص — وهذا الخطر المتبقي المُسجَّل في
  `docs/agent3-p0-adjudication.md`. الآن تُدفع نسخة كاملة إلى جدول Supabase
  (`state_snapshots`) خارج الخادم، فحذف الخدمة أو فقدان الـVolume لم يعد يعني فقدان الحالة.
- **الموصل**: `connectors/supabase_client.py` (REST عبر `urllib` — بلا أي اعتمادية جديدة)
  و`connectors/supabase_state.py` (دفع · عرض · فحص · استعادة · تقليم).
- **سلامة الاستعادة**: بصمة sha256 تُحسب على **تمثيل قانوني مرتَّب** (لأن عمود `jsonb`
  لا يحفظ ترتيب المفاتيح ولا التنسيق — البصمة على بايتات الملف الخام كانت ستُظهر كل نسخة
  «تالفة»). تُفحص البصمة والأقسام الأساسية قبل أي كتابة، وتُؤخذ نسخة محلية
  (`state-pre-restore-*.json`) ثم يُكتب الملف **ذرّيًا** (`os.replace`).
- **حواجز مقصودة**: الكتابة تحتاج مفتاحًا سريًا **و**`SUPABASE_WRITE_ENABLED=1` (مغلق
  افتراضيًا)، ومفتاح anon/publishable لا يكتب أبدًا، وجدول النسخ بـRLS مفعّل وبلا سياسات
  (مسدود على المفتاح العام)، والاستعادة **من الطرفية فقط** — لا أمر تيليجرام يلمس
  `state.json`. ولا يُطبع أي مفتاح في أي مخرَج (تنقية `redact()` لكل رسالة خطأ).
- **`.env` صار مقروءًا فعلًا**: `engine/env_file.py` يقرأ `.env` محليًا بلا اعتماديات،
  والمتغيرات الحقيقية في البيئة تتقدّم عليه دائمًا. القالب: `.env.example`.
- **الاستخدام**: `/backup_now` و`/backups` من تيليجرام · `python3 -m connectors.supabase_state
  push|list|show|restore|prune` · و`/diag` يعرض حالة القناة تلقائيًا.
- **تنزيل نسخة إلى قرصك**: `python3 -m connectors.supabase_state pull --id latest` — لأن
  الخطة المجانية في Supabase **لا تقدّم نسخًا احتياطية تلقائية ولا PITR** (مدفوعة ~$25/شهر)
  وتُوقف المشروع بعد 7 أيام خمول؛ فالسحابة ليست حصنًا بحد ذاتها، ووجود نسختين مستقلتين
  (عندك وفي السحابة) هو الضمان الحقيقي. والدفعة اليومية تُبقي المشروع مستيقظًا تلقائيًا.
- **الرحلة الكاملة** (الواجهة الحالية: Settings → **API Keys** أو زر **Connect**، مفاتيح
  `sb_publishable_…`/`sb_secret_…` الجديدة مقابل `anon`/`service_role` القديمة، جدولا SQL،
  الاستعادة، حل المشاكل): `docs/supabase-setup.md` · الاختبارات: `tests/test_supabase.py`
  و`tests/test_supabase_tasks.py` و`tests/test_supabase_e2e.py` (خادم PostgREST محلي —
  دورة كاملة بلا شبكة خارجية، 81 اختبارًا) · التحقق: `bash scripts/verify_supabase.sh`.

## الجديد في v1.1 (عتبة التفويض المالي — دفع تلقائي 375 ريال)
- **استثناء واحد ضيّق ومصرّح على قاعدة «المالي أحمر»**: التزام مالي **< 375 ريال (~100$)**
  يرتقي بفئة `money` من **L1 إلى L3** ← **دفع تلقائي** فعلي عبر موصل الدفع مع إيصال
  ومهمة مرئية وتقرير وزر تراجع (`undo` يطلب الاسترداد). القرار `ACT_PAY`/🟩 GREEN.
- **≥ 375 ريال أو مبلغ مجهول** ← **🟥 أحمر كما كان**: تنبيه فوري + مسودة
  `PENDING_APPROVAL`، **لا تنفيذ إطلاقًا** (`ALERT_DRAFT`).
- **الحواجز — لا يُنفَّذ شيء ما لم تتحقق كلها**: `MONEY_AUTOPAY_ENABLED=1` +
  `MONEY_AUTOPAY_ACK=I_AUTHORIZE_SUB_375_SAR_AUTOPAY` + موصل دفع مضبوط
  (`PAYMENT_GATEWAY_WEBHOOK_URL/SECRET`) + مبلغ معلوم موجب دون العتبة + **السقف اليومي
  التراكمي 375** (يعدّ النيّة المفوَّضة لا المستقر فقط) + **مفتاح عدم تكرار** (لا دفع مزدوج).
  أي حاجز ناقص ← يعود فورًا لمسودة الاعتماد، فالنشر بلا مفاتيح الدفع **آمن تمامًا**.
- **الحدود في الكود لا البيئة**: `HARD_MAX_SAR = 375.00` سقف صارم؛ متغيرات البيئة
  **تخفضه ولا ترفعه** أبدًا (لا خطأ مطبعي يوسّع التعرّض المالي).
- **ذرّية الحالة vs أثر الشبكة**: تُسجَّل النية `AUTHORIZED` داخل المعاملة، ويُنفَّذ الدفع
  **بعد** إقفالها (كنمط دفع تيليجرام)؛ فشل المزوّد/الشبكة موثَّق ولا يُسقط الدورة ←
  **مسودة احتياطية** في طابور الاعتماد (لا سقوط صامت لالتزام مالي).
- **دفتر تدقيق جديد** `autopay_executions` بمخزن الحالة + أحداث `autopay_authorized/
  executed/failed/blocked` في `audit.jsonl`.
- السياسة والتنفيذ: `connectors/payment_gateway.py` · القرار: `engine/proactive.py`
  (`decide` + `_execute_authorized_payments`) · موصل رملي للاختبار:
  `connectors/payment_sandbox.py` · المرجع: `docs/v1.1-money-threshold.md` ·
  الاختبارات: `tests/test_money_threshold.py` (18) · التحقق الكامل:
  `bash scripts/verify_money_threshold.sh` (بناء/مصفوفة/عتبة/وظيفي/مدير/جدولة/RAG).
- أوامر: `python3 engine/proactive.py threshold|matrix|status`.

## الجديد في v1.0 (رئيس المكتب الاستباقي — Proactive Chief of Staff)
- **حلقة استباقية كاملة** (`engine/proactive.py`): رصد ← تذكّر ← توقّع ← تسجيل نقاط ←
  قرار ← **تنفيذ/تجهيز/تنبيه** ← تعلّم، تعمل داخل معاملة Store واحدة وتُنادى تلقائيًا من
  `engine/manager.py --loop` (تعطيل فوري: `PROACTIVE_ENABLED=0`).
- **سجل الحلقات المفتوحة** (`open_loops`): التزاماتي لنفسي، التزامات الآخرين لي، تجديدات،
  قرارات، مخاطر مشاريع — يُغلق ما تحقق ولا يسقط مهم بصمت أبدًا.
- **سلّم استقلالية لكل فئة** (L0–L4): اتصالات/مالية/قانوني/صحي/سمعة ← L0/L1 (تجهيز
  واقتراح فقط)، وجدولة داخلية/تذكيرات/مهام/تحضير ← L2/L3 (تنفيذ قابل للعكس + تقرير).
  لا مفتاح «تصرّف بحرية» عام.
- **8 أوامر دائمة مصرّح بها** (`standing_orders`): تحضير اجتماع <30د، موعد <48س بلا نافذة،
  انتظار يتعفّن، استحقاق مالي <3 أيام، تجديد <7 أيام، تعارض مواعيد، سفر <24س،
  واستدراك التزام فائت — إيقاف أيٍّ منها: `order-disable SO-00x`.
- **استدراك ما فات** بصيغة إلزامية: «ما فات / الأثر / خيارات الاستدراك / ما فعلت / ما أحتاج».
- **الحواجز**: ثقة <0.8 ← تجهيز لا تنفيذ · سقف 6 تنبيهات/يوم والفائض يُدفع للبريف ·
  ساعات هدوء 22:00–06:30 · زر تراجع `undo PA-xxxx` لكل تنفيذ · مفتاح إيقاف
  `pause --hours 4` · سجل تدقيق كامل.
- **يتعلّم منك**: `feedback PA-xxxx good|much|never` — «أبدًا» توقف النوع، «كثير»
  يحصره في البريف 14 يومًا، والأحمر الحرج يتجاوزها موثَّقًا لحمايتك.
- **مراجعة الأسبوع وضبط العتبات من الواقع**: `python3 engine/proactive.py review`
  يحسب معدل القبول والتراجع وامتلاء السقف وإشارات التغذية، ويقترح بقواعد تحفظية
  محدودة تعديل `PROACTIVE_CONFIDENCE_THRESHOLD/PROACTIVE_MAX_ALERTS`، و`--apply`
  يخزّن التعديل في الحالة ليسري على الحلقة دون لمس متغيرات المنصة
  (حارس: لا تعديل قبل 5 قرارات فعلية).
- **قناة تنبيه تيليجرام المستعجلة**: بمجرد ضبط `TELEGRAM_BOT_TOKEN` (ومعرّف المحادثة
  كما في البوت القائم) تصلك تنبيهات `proactive_alert` فورًا للجوال — فقط ما اجتاز سقف
  اليوم وساعات الهدوء، وفشل الشبكة موثَّق ولا يُسقط الدورة. تحقق بضغطة واحدة:
  `python3 engine/proactive.py push-test` أو من البوت نفسه: `/proactive_test`
  (وللحالة `/proactive`، ولدورة فورية `/sweep`) (`PROACTIVE_TELEGRAM_PUSH=0` للإيقاف).
- **عامل الإنتاج الاستباقي**: يبدأ داخل Telegram webhook تلقائيًا كل 15 دقيقة
  (`PROACTIVE_WORKER_ENABLED=0` للإيقاف، و`PROACTIVE_WORKER_INTERVAL_SECONDS` للفاصل).
  يشغّل نفس الحواجز أعلاه؛ الرسائل الخارجية والمدفوعات والنشر تبقى `PENDING_APPROVAL`.
  يسجل `last_proactive_worker` بعد كل دورة ناجحة لتشخيص حداثة التشغيل.
- أوامر: `python3 engine/proactive.py sweep|brief|status|orders` ← بريف اليوم
  `reports/proactive-brief-YYYY-MM-DD.md`. حزمة الأوامر: `prompts/proactive-chief-of-staff.md`
  · المرجع: `docs/v1.0-proactive-chief-of-staff.md` · الاختبارات: `tests/test_proactive.py` (22).
- **لم تتغير قاعدة الحوكمة**: المحرك لا يرسل أي أثر خارجي أبدًا — كل ما يمس الخارج
  يبقى مسودة `PENDING_APPROVAL` خلف بوابة الاعتماد مهما بلغ مستوى الاستقلالية.

- **بريف الصباح**: «📚 مراجعات تعلّم اليوم (N دقائق)» بسقف مراجعتين.
- **بروتوكول التدريس الحي**: `prompts/personal-training.md` (فرز QUICK/COURSE، أسئلة استرجاعية موثقة بمصادر، تغذية راجعة بمخطط إلزامي).

## الجديد في v0.3.1 (تبني Voice Relationship Manager — Phase 1)
- **مُعالج المكالمات الواردة** (`engine/voice_call.py`): تفريغ المكالمة → تصنيف المتصل والنية → ملخص منظم → StateStore (جهات اتصال، مهام معاودة، waiting_for v2، عملاء محتملون، طلبات تحويل) + **مسودة متابعة إلى طابور الاعتماد** — لا إرسال إطلاقًا.
- **حمايات صارمة**: لا تشخيص من مكالمة، كلام المتصل = محتوى غير موثوق (محاولات الحقن تُرفض وتوثق أمنيًا)، Data Minimization، وidempotency بمعرف المكالمة.
- **قسم 📞 مكالمات في البريف واللوحة** (مرة واحدة لكل مكالمة — الأمني أولًا).
- جاهز للربط بأي مزود صوتي لاحقًا: `python3 engine/voice_call.py demo A|B|C|D|E` أو `ingest call.json`.

## الجديد في v0.3 (تبني Manager Loop من v4.1.1 الخارجية)
- **حلقة المدير بدورتين** (`engine/manager.py`): سريعة كل 15 دقيقة (مسح حتمي للانتظار) + كاملة 06:00 بتوقيت الرياض (بريف + لوحة) — مع catch-up لو فوّت التشغيلة، وwrite-on-change.
- **waiting_for schema v2**: آلة حالات WAITING→OVERDUE، وإجراء متابعة واحد لكل عنصر متأخر (idempotent)، ومسودة متابعة جاهزة.
- **decision_requests**: طلب قرار رسمي (خيارات + مهلة) للمشاريع النشطة المتوقفة فعليًا — حله يسجل في سجل القرارات بمراجعة بعد 30 يومًا، والخيار «تحويل إلى متوقف» ينفَّذ فعليًا.
- **كشف تغيّر الحالة**: قسم «🔄 ما تغيّر منذ البريف السابق» (جديد/تغيّر حالة/أُغلق).

## الجديد في v0.2 (إصلاحات C1 + C2 من المراجعة المعمارية)
- **State Store موحد** (`data/state.json`): الكاتب الوحيد لكل البيانات القابلة للتغيير — كتابة ذرّية، رقم إصدار يرفض التعارض، نسخ احتياطية دوّارة (آخر 5)، وسجل تدقيق `data/audit.jsonl`. **الشيت أصبح صيغة استيراد/تصدير فقط.**
- **طابور الإجراءات + بوابة اعتماد**: مسودات المتابعة تُدرج تلقائيًا كإجراءات `PENDING_APPROVAL` في `reports/approvals-latest.html`، ولا تُعتمد إلا بأمر يحمل **بصمة SHA-256 لنصها** (`python3 engine/approve.py approve A-001 --hash ...`)، وتنتهي صلاحيته بعد 48 ساعة، ولا يتكرر أبدًا (idempotency).
- **تعفّن الانتظار**: كل ما تنتظره (رد عميل، تحرك مشروع) يُشتق في `waiting_for` ويظهر في البريف، وما تجاوز 14 يومًا يُرفع كقضية قرار.

## الربط بالخدمات الخارجية (Sheets · Drive · Docs · Calendar · GitHub)
- فحص فوري لحالة كل القنوات: `python3 -m connectors.connection_setup` (أضف `--live` للفحص الحي عبر الشبكة، و`--guide calendar` لخطوات قناة محددة).
- **Kimi API (تجاوز حد Gemini ~20 سؤال/يوم):** أضف في Railway `KIMI_API_KEY` من platform.moonshot.ai. اختياري: `KIMI_MODEL=kimi-k2.5` و`KIMI_BASE_URL=https://api.moonshot.ai/v1`. اترك `AI_MODEL_PROVIDER=gemini` ليُستخدم Kimi تلقائيًا بعد نفاد الحصة، أو اضبط `AI_MODEL_PROVIDER=kimi` لاستخدامه مباشرة. الأسئلة السريرية تبقى على Gemini ما لم تضبط `AI_CLINICAL_PROVIDER=kimi`. لا تضع المفتاح في Git أو في المحادثة.
- خطوات الربط كاملة مع متغيرات البيئة المطلوبة: `docs/connection-guide.md` — **مفاتيح الربط توضع في متغيرات البيئة فقط، ولا تُرسل في أي محادثة**.
- **Supabase (نسخ الحالة خارج الخادم — اختياري):** `docs/supabase-setup.md`. ضع `SUPABASE_URL` و`SUPABASE_SERVICE_ROLE_KEY` و`SUPABASE_WRITE_ENABLED=1` في Railway → Variables (لا في Git ولا في محادثة)، وشغّل SQL الإعداد مرة واحدة: `python3 -m connectors.supabase_client --sql`. ثم `/backup_now` من تيليجرام. المفتاح السري يبقى على الخادم فقط؛ ومفتاح anon/publishable للقراءة فقط ولا يكتب أبدًا.
- نقل التشغيل إلى Railway، المتغيرات، الـVolume، وتشخيص انتهاء بيئة 24 ساعة: `docs/railway-migration.md`.
- خطابات وتقارير رسمية عبر Google Docs: `python3 -m connectors.google_docs_service create "العنوان" "النص"` (تُنشأ كمسودات — الإرسال الخارجي يبقى خلف بوابة الاعتماد).

## Telegram Bot — أوامر الجوال

تمت إضافة بوت polling فعلي في `connectors/telegram_bot.py`، وهو مستقل عن ملف فحص الاتصال `connectors/telegram_live.py`.

الأوامر:
- `/start` و`/help`: بدء الاستخدام وعرض القائمة.
- `/profile`: الملف المهني المختصر.
- `/sources`: عدّ مصادر المعرفة والمهارات والمواد.
- `/selftest`: فحص Telegram ومكونات النظام الأساسية.
- `/youtube كلمات` (أو `/search`): بحث يوتيوب بروابط `watch?v=` موثّقة — لا روابط مخترعة.
- `/storage_status`: فحص اتصال الحفظ عند الطلب.
- `/content [platform] الفكرة`: تشغيل أوركسترا المحتوى (باحث ← ناقد ← منشئ) وإرجاع Preview.
- `/approve_content ID CODE`: إرسال النسخة المعتمدة إلى Buffer مع حفظ الإيصال.
- `/reject_content ID`: رفض المسودة دون أي أثر خارجي.
- `/content_status`: حالة Content Creator وBuffer وآخر المسودات.

الوضع الافتراضي لـContent Creator هو `linkedin` وBuffer `draft`. يمكن ضبطهما عبر
`CONTENT_DEFAULT_PLATFORM` و`BUFFER_DEFAULT_MODE`. يمكن ربط وكيل المحتوى بورقة
تشغيل مستقلة عبر `CONTENT_SHEET_ID` (ويستخدم افتراضيًا
ورقة `life_pulse_content_engine`) ثم `/content_sheet Q-001` أو `/content_sheet`
لأول صف Ready/Idea. يكتب المسودة في `PUBLISH_QUEUE` ويظل الإرسال إلى Buffer خلف
`/approve_content ID CODE`. استخدم `/content_sheet_status` لفحص صلاحية القراءة.
لا ينشر أي نموذج مباشرة؛ جميع النسخ تدخل `action_queue` أولًا ولا يصل Buffer إلا
بعد رمز الموافقة الخاص بالمسودة.

الرد العادي يبدأ بالنتيجة أو المسودة المطلوبة، وبجملة أو جملتين افتراضيًا؛
التفصيل يكون عند طلبه أو لضرورة السلامة. لا تُضاف قوائم ملفات المعرفة أو إشعارات
فحص الذاكرة أو إيصالات حفظ المحادثة تلقائيًا. يستمر الحفظ الداخلي بعد فحص الخصوصية،
وتُسجّل أخطاؤه في سجلات التشغيل؛ التشخيص متاح عبر `/sources` و`/storage_status`.
إيصالات الإجراءات الفعلية ومعاينتها وموافقتك قبل التنفيذ لا تتغير.

التشغيل:

```bash
export TELEGRAM_BOT_TOKEN="ضع_التوكن_في_بيئة_التشغيل_فقط"
python3 -u connectors/telegram_bot.py
```

للحماية الإضافية، يوصى بضبط `TELEGRAM_ALLOWED_CHAT_ID`. إذا لم يُضبط، تصبح أول محادثة خاصة تستخدم البوت هي المالك المحلي، ويُحفظ المعرّف في ملف متجاهل من Git.

> لا تضع التوكن داخل GitHub. استخدم Secrets أو Environment Variables في منصة الاستضافة.

## Executive brief discovery and supervisor reports

- `/brief` reads a bounded live Sheets snapshot, compares it with the last
  persisted snapshot, detects changes, incomplete items, upcoming dates,
  blockers, decisions, and important information, then updates
  `Executive_Brief`.
- The comparison snapshot is stored below `AI_OS_DATA_DIR`. On Railway, mount
  a persistent volume at `/data` and set `AI_OS_DATA_DIR=/data`.
- Deploy `connectors/google_sheets_webhook.gs` as the secure Sheets gateway.
  Set Script Properties `SPREADSHEET_ID` and `AGENT_SECRET`; set the matching
  Railway variables `GOOGLE_SHEETS_WEBHOOK_URL` and
  `GOOGLE_SHEETS_WEBHOOK_SECRET`.
- Copy `connectors/rehab_supervisor_form.gs` into a Google Apps Script project,
  run `createRehabSupervisorForm` once, authorize it, then run
  `testRehabIntegration`. Re-running creation returns the existing form unless
  `createRehabSupervisorForm(true)` is used intentionally.
