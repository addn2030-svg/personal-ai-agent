# AI OS v1.0 — رئيس المكتب الاستباقي (Proactive Chief of Staff)

> الإصدار: v1.0 — تحويل الوكيل من «يستجيب عند السؤال» إلى **يمسح ويتوقّع ويمنع
> ويُجهّز وينفّذ ضمن حدود آمنة** بشكل مستمر.
> القاعدة الحاكمة: **نفّذ-أولًا للقابل للعكس/منخفض الخطورة؛ اسأل-أولًا لغير
> القابل للعكس/عالي الخطورة.** وقاعدة الحوكمة (v4.1.1) تعلو كل شيء: **لا أثر خارجي
> إلا عبر طابور الاعتماد** — مهما بلغ مستوى الاستقلالية.
> حزمة الأوامر المرافقة: `prompts/proactive-chief-of-staff.md`.

## 1. الغرض

الهدف ليس وكيلًا يقاطعك باستمرار، بل وكيل **يُغلق الحلقات بهدوء، يمنع الفوات،
ولا يرفعه إلا ما يستحقك فعلًا** — مع حقك الكامل في التراجع والإيقاف والتعليم.

| قبل v1.0 | بعد v1.0 |
|---|---|
| سريعة تكشف المتأخر فقط (`manager.py fast`) | حلقة كاملة: رصد ← تذكّر ← توقّع ← تسجيل نقاط ← قرار ← تنفيذ/تجهيز/تنبيه ← تعلّم |
| كل شيء مسودة أو تقرير | تنفيذ داخلي قابل للعكس (مستوى L2/L3) + تجهيز خارجي (L1) + اقتراح (L0) |
| أعطيتَه أمرًا فيعمل | أوامر دائمة مصرّح بها مسبقًا تعمل وحدها |
| ما فات يظهر في البريف التالي | ما فات يُكتشف ويُستدرك فورًا بصيغة «ما فات/الأثر/الخيارات/ما فعلت/ما أحتاج» |

## 3. الحلقة بالتفصيل (كيف تعمل الدورة)

كل استدعاء `sweep()` يحدث داخل **معاملة Store واحدة** (write-on-change؛ لا كتابة
ولا نسخة احتياطية إن لم يتغير شيء):

1. **رصد:** قراءة `tasks` `meetings` `waiting_for` `finance` `decision_requests`
   `projects` `okrs` …
2. **تذكّر (Open Loops Ledger):** `refresh_open_loops` يبني/يحدّث سجل الالتزامات
   بمعرف حتمي (`OL-xxxx` = نوع+عنوان): التزاماتي لنفسي (`i_promised`)، التزامات
   الآخرين (`they_promised`)، تجديدات (`renewal`)، قرارات (`decision`)، مخاطر
   مشاريع متوقفة (`risk`). ما تحقق مصدره يُغلق، وما تغيّر مادّيًا يُعاد فتحه.
3. **توقّع:** `collect_candidates` — دوال نقية (لا كتابة) تولّد المرشحين بمفاتيح
   منع-تكرار.
4. **تسجيل النقاط:** `score = أثر(1–5) × استعجال(1–5) × ثقة(0–1) × عامل الخطورة
   (1.0/0.85/0.6)`، وغير القابل للعكس ×0.7.
5. **قرار:** `decide` يربط النقاط بسلّم الاستقلالية وحالة التغذية الراجعة.
6. **تنفيذ/تجهيز/تنبيه:** حسب المسار (انظر §4) + حواجز الحماية (§7).
7. **استدراك:** `recovery_pass` يقارن المتوقع بالفعلي على سجل الحلقات.
8. **تعلّم:** `feedback/undo/pause` يعدّلون سلوك الدورات اللاحقة.

### تغطية أنواع المحفزات الستة

| النوع | المنفَّذ حتميًا الآن | يحتاج موصلًا حيًا لاحقًا |
|---|---|---|
| زمني | اجتماع <30د (SO-001) · موعد <48س (SO-002) · سفر <24س (SO-007) · مالي <3 أيام (SO-004) · تجديد <7 أيام (SO-005) | ميلاد/اشتراكات من الروزنامة الحية |
| حدثي | طلب قرار تقترب مهلته · انتظار بلا رد (SO-003) | بريد VIP وارد، تغيّر اجتماع |
| حالوي | مشروع نشط بلا تقدم 30يوم (حلقة `risk` + طلبات القرار في manager) | — |
| نمطي | مهمة تنزلق ≥7 أيام ← قرار ثلاثي (جدولة/تفويض/حذف) | «عادة الأحد» من سجل السلوك |
| شاذ | تعارض مواعيد 60د (SO-006) · انقطاع رد مطوّل | صمت غير معتاد من قناة حية |
| فرصي | أول فجوة تركيز ≥90د اليوم (اقتراح) · اشتراك غير مستخدم ≥45يوم (توفير مُقدَّر) | خصم تجديد، لحظة شبكة علاقات |

## 4. سلّم الاستقلالية (AUTONOMY_MATRIX)

| الفئة | المستوى | السلوك العملي في المحرك |
|---|---|---|
| external_comms | L1 | مسودة كاملة في `action_queue` ← اعتماد بنقرة (لا إرسال آلي أبدًا) |
| money | L1 | تنبيه + تعليمة دفع/قرار تجديد كمسودة معتمدة؛ لا أموال تتحرك آليًا |
| legal / health | L0 | اقتراح وتنبيه فقط |
| reputation | L1 | مسودة اعتذار/إعادة جدولة للاعتماد |
| internal_sched / reminders | L3 | حجز نافذة تركيز/مهمة استدراك في `tasks` + تقرير |
| task_creation / prep_work | L2 | إنشاء مهام/ملاحظات تحضير + تقرير |

تحويل المستوى إلى قرار (دالة `decide`):

- 🟩 **ACT** — يتطلب *كل*: مستوى ≥L2 ∧ قابل للعكس ∧ خطورة منخفضة ∧ أمر دائم مصرّح
  ∧ ثقة ≥ 0.8 (وإلا يُخفَّض إلى PREPARE — قاعدة العتبة).
- 🟨 **PREPARE** — مستوى ≥L1 والمرشح من نوع «تجهيز» ← مسودة في طابور الاعتماد
  (idempotent ببصمة المحتوى مثل `manager.py`).
- 🟥 **ALERT / ALERT_DRAFT** — خطورة عالية أو غير قابل للعكس أو فئة حرجة مستعجلة
  ← تنبيه فوري وتوصية (ومسودة اختيارية إن وُجد أمر دائم مصرّح). **لا تنفيذ آلي
  للأحمر أبدًا، ولا يُخفَّض بتفضيل «أبدًا» — يُوثَّق التجاوز.**
- ⚪ **SUGGEST** — L0 أو خفض تغذية «كثير» ← يظهر في البريف فقط.

ما يُنفَّذ أخضرًا هو عمليات داخلية قابلة للعكس حصرًا (إنشاء مهمة بمصدر
`proactive:PA-xxxx`)، وكل صف `proactive_actions` يحمل حمولة `undo` حرفية.

تُزرع الثمانية في `standing_orders` عند أول دورة وتُدار من الحالة (لا من الكود):

| # | الأمر | فئة/مستوى |
|---|---|---|
| SO-001 | اجتماع <30د ← ملاحظة تحضير وجدول أعمال | prep_work/L2 |
| SO-002 | موعد <48س بلا نافذة ← حجز نافذة تركيز | internal_sched/L2 |
| SO-003 | انتظار بلا رد ≥3 أيام قبل التعفّن ← مسودة متابعة | external_comms/L1 |
| SO-004 | استحقاق مالي ≤3 أيام ← تنبيه أحمر + تعليمة دفع للاعتماد | money/L1 |
| SO-005 | تجديد ≤7 أيام ← تلخيص + مذكرة قرار | money/L1 |

| SO-007 | سفر <24س ← وثائق + مسار + مسودة check-in | prep_work/L1 |

## 6. استدراك ما فات (Missed-Action Recovery)

`recovery_pass` يقارن المتوقع بالفعلي على سجل الحلقات في كل دورة:

1. حلقة `OPEN` تجاوز موعدها ← `MISSED` (حدث `proactive_missed` في التدقيق).
2. يقدَّر الأثر من أثر الحلقة ونوعها، وتُولَّد خيارات استدراك حسب النوع:
   `they_promised` ← مسودة متابعة للاعتماد (خارجي → L1). `renewal` ← تنبيه أحمر +
   تعليمة للاعتماد. `i_promised/decision/risk` ← مهمة استدراك داخلية (أخضر → L2).
3. تنفيذ حسب المسار ثم الحالة `RECOVERING` مع رابط الإجراء — **مرة واحدة لكل
   حلقة يوميًا، ولا يسقط مهم بصمت أبدًا.**
4. التقرير داخل جسم الإجراء بالصيغة الإلزامية: «ما فات / الأثر / خيارات الاستدراك /
   ما فعلت / ما أحتاج».

## 8. واجهة الأوامر

```bash
python3 engine/proactive.py sweep        # دورة رصد كاملة (تُنادى أيضًا من manager --loop)
python3 engine/proactive.py brief        # بريف اليوم → reports/proactive-brief-YYYY-MM-DD.md
python3 engine/proactive.py status       # الحالة: فعّالة/موقوفة/هدوء/عدادات/أوامر
python3 engine/proactive.py orders       # عرض الأوامر الدائمة
python3 engine/proactive.py order-disable SO-003   # (والعكس order-enable)
python3 engine/proactive.py matrix       # مصفوفة الاستقلالية
python3 engine/proactive.py pause --hours 4  | resume
python3 engine/proactive.py undo PA-0001
python3 engine/proactive.py feedback PA-0001 good|much|never [--scope category]
```

كل الإعدادات قابلة للضبط بالبيئة: `PROACTIVE_ENABLED` · `PROACTIVE_CONFIDENCE_THRESHOLD`
· `PROACTIVE_MAX_ALERTS` · `PROACTIVE_QUIET_START/END` · نوافذ المحفزات
(`PROACTIVE_MEETING_WINDOW_MIN`، `PROACTIVE_DEADLINE_WINDOW_H`، `PROACTIVE_AGING_DAYS`…).

## 9. التكامل مع المكونات القائمة

- **حلقة المدير:** `manager.py --loop` ينادي `sweep()` بعد مُرسل الجدولة، معزولًا
  بـtry/except ومسجَّلًا `proactive_error` عند الفشل — دورة المدير لا تتعطل.
- **بوابة الاعتماد:** المسودات تظهر في `reports/approvals-latest.html` وتُعتمد
  ببصمة المحتوى عبر `engine/approve.py` — لا قناة ثانية للموافقات.
- **البريف الصباحي:** مهام المحرك (النوع «استباقي») تظهر ضمن مهام `chief_of_staff.py`
  المفتوحة، والبريف الاستباقي ملف مستقل يمكن إلحاقه لاحقًا بوظيفة الجدولة الصباحية.
- **تيليجرام:** أحداث `proactive_alert` مسجلة في التدقيق جاهزة للربط بقناة دفع
  مستقبلية (خارج نطاق هذا الإصدار — التنبيهات تُقرأ من البريف و`status`).

## 10. التشغيل الأول (قائمة الحد الأدنى)

1. النطاقات الثلاثة الجاهزة: مواعيد ← `meetings`، مهام ← `tasks`، مراسلات/انتظار ← `waiting_for`.
2. شغّل أول دورة يدويًا وراجع الدفتر: `python3 engine/proactive.py sweep` ثم `status`.
3. راجع مصفوفة الاستقلالية وعدّلها لذوقك (ثم التزم بها أسبوعًا).
4. اربطه بالحلقة في الإنتاج (فعّال افتراضيًا؛ `PROACTIVE_ENABLED=0` للإيقاف الفوري).
5. اعتمد تدفق البريف اليومي: `python3 engine/proactive.py brief` صباحًا.
6. درّبه أسبوعين بـ`feedback`، ثم راجع العتبات أسبوعيًا (معدل القبول، الإنذارات الكاذبة).

## 11. حدود صريحة (ما لا يفعله)

- لا يرسل ولا يدفع ولا ينشر ولا يحذف خارجيًا — **أبدًا**، ولو طلبتَ ذلك منه آليًا.
- لا يقرأ بريدك/تقويمك الحي بنفسه — يتغذى من أقسام الحالة (الموصلات الحية تُغذيها
  عبر مسارات `v0.8/v0.9` القائمة).
- «L4» محجوز: التنفيذ الأخضر الحالي = عمليات داخلية قابلة للعكس فقط.
- الأحمر يتجاوز «أبدًا» والهدوء (بتوثيق) — هذه ميزة سلامة لا خطأ.
