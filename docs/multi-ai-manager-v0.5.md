# Active Multi-AI Manager v0.5

## Goal

Allow ChatGPT, Claude, Gemini and later advisers to submit structured updates into one Manager without giving those external AIs direct ownership of operational state.

## Where data lives

### GitHub — code only
Repository files contain application code, tests and documentation. API keys, Telegram tokens and service-account JSON must never be committed.

### Railway persistent volume — operational memory
Set `AI_OS_DATA_DIR=/data` and mount a Railway persistent volume at `/data`.

Important files:
- `/data/state.json` — operational source of truth.
- `/data/audit.jsonl` — append-only audit events and StateStore commits.
- `/data/backups/` — rotating StateStore backups.
- `/data/30-state-backups/` — migration backups created by the hardening release.

Important StateStore sections for v0.5:
- `unified_inbox` — every normalized incoming update.
- `ai_sources` — adviser registry, role, trust level, last seen, event counts.
- `contradictions` — explicit external-AI conflicts requiring reconciliation.
- `decision_requests` — owner decisions generated by the Manager.
- `conversation_memory` — bounded conversation memory already used by the runtime.
- `manager_markers` — Manager cycle markers.

### Google Sheets — human input + projection
Sheets remains a human-editable input/projection surface. It is not the operational source of truth for machine-owned fields.

### Railway Variables — secrets and connector configuration
Never store these in `state.json`, Sheets or GitHub.

Existing production variables remain required. Multi-AI v0.5 adds one key per adviser, for example:

```text
AI_GATEWAY_CHATGPT_KEY=<long-random-secret>
AI_GATEWAY_CLAUDE_KEY=<long-random-secret>
AI_GATEWAY_GEMINI_KEY=<long-random-secret>
```

Optional consolidated form:

```text
AI_GATEWAY_KEYS_JSON={"chatgpt":"...","claude":"...","gemini":"..."}
```

Use either the individual variables or JSON mapping. Individual keys override the same source from the JSON mapping.

Optional path overrides:

```text
AI_GATEWAY_UPDATE_PATH=/api/ai/update
AI_GATEWAY_HEALTH_PATH=/api/ai/health
```

## External AI request contract

HTTP request:

```text
POST https://<railway-domain>/api/ai/update
Authorization: Bearer <source-specific-key>
X-AI-Source: claude
Content-Type: application/json
```

Body:

```json
{
  "event_id": "claude-20260827-001",
  "type": "RISK",
  "summary": "Railway persistent volume may not be mounted",
  "project": "personal-ai-agent",
  "confidence": 0.91,
  "urgency": "HIGH",
  "evidence": ["Deployment configuration review"],
  "proposed_action": "Verify /data persistence before merge",
  "requires_confirmation": false,
  "sensitive": false
}
```

Supported types:

```text
TASK
REQUEST
DECISION
WAITING_FOR
FACT
DOCUMENT
IDEA
APPOINTMENT
RISK
OPPORTUNITY
BLOCKER
PROJECT_UPDATE
STATUS_CHANGE
RECOMMENDATION
CONTRADICTION
EXTERNAL_AI_RESULT
```

Urgency:

```text
LOW | NORMAL | HIGH | CRITICAL
```

## Safety model

External advisers are advisory sources. They cannot directly:
- mutate tasks/projects;
- create or delete Calendar events;
- send WhatsApp/email/Telegram messages on the owner's behalf;
- overwrite StateStore operational fields;
- bypass approval/decision gates.

Flow:

```text
External AI
  -> authenticated AI Gateway
  -> Unified Inbox
  -> source attribution + stable event dedup
  -> reactive AI Manager review
  -> optional decision request / contradiction
  -> existing Manager fast cycle
  -> owner approval where required
```

High/critical updates and `RISK`, `BLOCKER`, `CONTRADICTION`, `STATUS_CHANGE`, `APPOINTMENT` wake the reactive Manager immediately. Routine advisory updates remain stored and appear in `/brief`.

## Telegram

`/agents` shows:
- registered AI advisers;
- role and trust level;
- last contact;
- number of received events;
- open contradictions;
- pending AI-originated decisions.

`/brief` now treats external-AI updates as advisory evidence, labels their provenance, and surfaces AI-team conflicts instead of silently merging claims.

## Health checks

```text
GET /health
GET /ready
GET /api/ai/health
```

`/api/ai/health` does not reveal keys. It only lists configured source names.

## Rollout order

1. Merge and deploy PR #12 hardening first after its staging gates pass.
2. Deploy v0.5 to an isolated staging Railway service/volume.
3. Add three staging keys: ChatGPT, Claude, Gemini.
4. Test `/api/ai/health`.
5. Send one `PROJECT_UPDATE` from each source.
6. Send one duplicate event and confirm only one Unified Inbox record exists.
7. Send a `RISK` and confirm the Manager creates one decision request.
8. Send a `CONTRADICTION` and confirm one contradiction record is created.
9. Run `/agents` and `/brief` in Telegram.
10. Redeploy twice and verify `ai_sources`, `unified_inbox`, and StateStore version persist.

Do not add Kimi/DeepSeek until the three-primary-agent workflow is stable and useful.
