# من Git إلى SQL — ما هي البيانات الموجودة، وكيف تُنقل خطوة بخطوة

> الغرض: الإجابة على سؤال «هل نستفيد من البيانات الموجودة في Git، وهل يمكن نسخها
> إلى SQL؟» ببيانات مقيسة فعلًا من المستودع، ثم خطوات قابلة للتنفيذ بالترتيب.
> كل رقم في هذا الملف مأخوذ من تشغيل حقيقي على المستودع، لا من تقدير.

---

## 0) الخلاصة في ثلاثة أسطر

1. **البيانات الحقيقية للوكيل ليست في Git**: `data/state.json` و`data/audit.jsonl`
   و`data/backups/` كلها في `.gitignore`. ما تحمله Git هو **البيانات المصدرية**
   (`data/master-sheet.xlsx`) وملفات المعرفة.
2. **نسخها إلى SQL ممكن ومفيد** — والطريق مبني ومُختبَر: الشيت → `state.json` →
   `state_snapshots` (+ `tasks_mirror` اختياريًا) → والبوت على Render يستعيدها عند
   كل إقلاع (خطة Render المجانية **بلا قرص دائم**، فالذاكرة تُفقد بلا هذا الملف).
3. **ثلاثة عيوب حقيقية ظهرت أثناء التحقق وأُصلحت**: الترحيل كان يتوقف بلا
   `openpyxl`، والتواريخ كانت تُرحَّل **بيوم ناقص**، والبيانات السريرية كانت
   **ستُرفع** إلى السحابة. التفاصيل في القسم 4.

## 1) ما هو موجود فعلًا في Git (مقيس)

| الملف | المحتوى | يُنقل إلى SQL؟ |
|---|---|---|
| `data/master-sheet.xlsx` | **11 ورقة · 106 صف** — الشيت الرئيسي (مهام 13 · مشاريع 11 · عملاء وفرص 8 · مؤشرات القسم 30 · مواعيد 4 · قرارات 5 · متابعة مرضى 6 · صندوق الصوت 4 · تعلم 5 · مالية 8) | ✅ **نعم** — هذا هو المقصود بالنقل. بيانات تشغيلية حقيقية |
| `prompts/*.md` (16 ملفًا) | شخصية الوكيل وسلوكه وقواعده | ❌ **لا** — تعليمات لا ذاكرة. نسخها إلى SQL = مصدر حقيقة ثانٍ يتباعد صامتًا |
| `training/rcjy-chief-of-staff-scenarios.md` | سيناريوهات تدريب | ❌ لا — نفس السبب |
| `evaluation/*.json` · `*.md` · `test_*.py` | حالات اختبار (5 حالات سياق · 6 حالات تحسّن) | ❌ لا — تُشغَّل في CI، ليست ذاكرة تشغيلية |
| `posts/buffer/*.json` | مسودة محتوى | ❌ لا |
| `data/state.json` · `data/audit.jsonl` · `data/backups/` | الحالة والتشغيل الفعلي | ⛔ **غير موجودة في Git** (مستثناة في `.gitignore:2-11`) |

**لماذا لا تُنسخ ملفات المعرفة إلى SQL؟** لأنها مصدر الحقيقة لسلوك الوكيل؛ ونسخها
إلى قاعدة البيانات ينشئ نسخة ثانية تتقادم بصمت — وهو ما رُفض صريحًا في
`docs/agents-tips-review.md` وفي `docs/supabase-rollout.md:144`.

## 2) الطريق الكامل

```
data/master-sheet.xlsx        (في Git · 106 صفًا)
        │  engine/migrate.py            ← ترحيل لمرة واحدة
        ▼
data/state.json               (على الجهاز · مصدر الحقيقة · single writer)
        │  connectors.cloud_payload     ← فلتر: ما يجوز أن يغادر الجهاز
        ▼
Supabase                      (state_snapshots · tasks_mirror · brain_*)
        │  state_persistence (AI_OS_STATE_RESTORE_ON_BOOT=1)
        ▼
Render free                   (بلا قرص دائم → يستعيد الذاكرة عند كل إقلاع)
```

## 3) الخطوات

### الخطوة 0 — على Supabase (يدويًا من لوحة التحكم · مرة واحدة)

SQL الإعداد يجب أن يكون موجودًا قبل أي رفع. اطبع الملفات ثم نفّذها في
**SQL Editor** بالترتيب:

```bash
python3 -m connectors.supabase_client --sql         # 01_state_snapshots.sql
python3 -m connectors.supabase_client --sql tasks   # 02_tasks_mirror.sql
python3 -m connectors.brain --sql                   # 03_brain_memory.sql
```

**التحقق**: الجداول `state_snapshots` · `tasks_mirror` · `brain_episodes` ·
`brain_facts` · `brain_working` موجودة في Table Editor.

---

### الخطوة 1 — الترحيل (على جهازك · بلا شبكة)

```bash
cp data/state.json /tmp/state-backup-$(date +%F).json    # احتياط قبل أي شيء
python3 engine/migrate.py                                # إن وُجد state.json: أضف --force
```

**المتوقّع**:
```
قارئ الشيت: stdlib
✅ رُحّل الشيت إلى data/state.json — 94 صفًا في 10 أقسام + 5 عنصر انتظار مُشتق.
```

> «اقرأني» ورقة دليل استخدام ولا تُرحَّل (10 أقسام فقط). `stdlib` تعني أن الترحيل
> يعمل بلا `openpyxl`؛ وإن كانت مثبَّتة ستظهر `openpyxl`.

**التحقق**:
```bash
python3 -c "import json;d=json.load(open('data/state.json'));print({k:len(v) for k,v in d.items() if isinstance(v,list) and v})"
# المتوقّع: tasks:13 · projects:11 · leads:8 · kpis:30 · meetings:4 · decisions:5
#          followups:6 · voice:4 · learning:5 · finance:8 · waiting_for:5
```

**لماذا هذا آمن**: `engine/migrate.py` يرفض العمل إن وُجد `state.json` إلا بـ`--force`،
فلا يدهس حالة قائمة بلا قرار منك.

### الخطوة 3 — الرفع إلى SQL (على جهازك · يحتاج مفاتيح)

```bash
export SUPABASE_URL="https://<project>.supabase.co"
export SUPABASE_SERVICE_ROLE_KEY="..."      # المفتاح السري
export SUPABASE_WRITE_ENABLED=1
python3 -m connectors.supabase_state push --reason "ترحيل الشيت الرئيسي"
```

**التحقق**:
```bash
python3 -m connectors.supabase_state list --limit 5    # النسخة ظهرت
python3 -m connectors.supabase_state show --id <N>     # الحمولة بلا صفوف مرضى
```

**اختياري — مرآة المهام** (جدول `tasks_mirror`، يسهل الاستعلام والتصفية):
```bash
python3 -m connectors.supabase_tasks sync --dry-run    # معاينة
python3 -m connectors.supabase_tasks sync
```

**اختياري — الدماغ**: `python3 -m connectors.brain --import` ينقل ذاكرة المحادثة
و`data/memory/*.jsonl`. لا شيء منه موجود بعد (بداية جديدة) — يعمل لاحقًا بعد
استخدام البوت. الوثائق: `docs/brain-durable-memory.md`.

### الخطوة 4 — Render (إعداد موجود في `render.yaml`)

الرايات المطلوبة (كلها مُعرَّفة في `render.yaml`):

| المتغير | القيمة | الأثر |
|---|---|---|
| `AI_OS_STATE_RESTORE_ON_BOOT` | `1` | استعادة آخر نسخة عند الإقلاع إن فُقدت الحالة |
| `AI_OS_STATE_PERSIST` | `1` | دفع تفاضلي تلقائي كل `AI_OS_STATE_PERSIST_SECONDS` (120 ث) |
| `SUPABASE_URL` · `SUPABASE_SERVICE_ROLE_KEY` | من Supabase | الوصول |
| `SUPABASE_WRITE_ENABLED` | `1` | السماح بالكتابة |

**التحقق بعد النشر**: البوت يقلع، و`/tasks` في تيليجرام يُظهر المهام الـ13
(و`python3 -m connectors.supabase_tasks stats` يعرض العدد من الحالة) — أي أن الذاكرة وصلت.

**الاستعادة القسرية** (لتصحيح يدوي): `AI_OS_STATE_RESTORE_FORCE=1` يكتب فوق حالة
محلية موجودة. بلا هذه الراية، الحالة المحلية أولًا.

**تذكير مهم**: خطة Render المجانية بلا قرص دائم، ولا يجب أن تكون النسخة السحابية
قديمة. اعمل `push` قبل أي إيقاف/إعادة نشر يدوي.

## 4) ثلاثة عيوب حقيقية ظهرت أثناء التحقق

لم يكن التحقق شكليًا؛ ظهرت ثلاثة أمور كانت ستُفسد النقل بصمت:

1. **التواريخ تُرحَّل بيوم ناقص.** كان قارئ xlsx يعالج «عملاق» Excel (1900-02-29
   الوهمي) في الاتجاه المعاكس، فتصبح `46248` = 2026-08-13 بدل **2026-08-14**. كشفه
   اختبار على الشيت الحقيقي، وصُحّح ودُعم بثلاث مراجع مؤكَّدة: `61 → 1900-03-01` ·
   `25569 → 1970-01-01` · `45292 → 2024-01-01`.
2. **الترحيل يتوقف بلا `openpyxl`.** أُضيف `engine/sheet_reader.py` — قارئ بالمكتبة
   القياسية فقط — فصار الترحيل يعمل في أي بيئة (و`openpyxl` تبقى المسار المفضّل
   إن وُجدت).
3. **البيانات السريرية كانت ستُرفع للسحابة.** `supabase_state.push` كان يرفع الحالة
   **كاملة**. أُضيف `connectors/cloud_payload.py`:
   - قسم `followups` (6 صفوف) يُفرَّغ — مع إبقاء مفتاحه كي لا ينكسر الاسترجاع؛
   - **المحتوى السريري في الأقسام الأخرى يُحجب أيضًا**: ملاحظة صوتية كانت تقول
     «والمريض أحمد يحتاج مراجعة للخطة» داخل قسم `صندوق الصوت` غير السريري. هذا
     التسريب عبر الأقسام هو ما أثبت أن استثناء القسم وحده لا يكفي؛
   - التمييز مقصود: «**المرضى**» في مؤشرات القسم (30 صفًا، إحصاء إداري) **لا تُمس**،
     أمّا «**المريض أحمد**» فيُحجب؛
   - الحجب **مُعلَن** في `meta` (`cloud_withheld` · `cloud_clinical_redactions`) حتى
     لا يظن أحد أن النسخة كاملة.

**تحقق بنفسك من أن هذه الحماية فعّالة**: تعطيل الفلتر سريريًا يُفشل 5 اختبارات،
وحذف استثناء `followups` يُفشل 4 اختبارات وواحدًا بخطأ — أي أنها اختبارات قادرة
على الفشل لا اختبارات شكلية. المجموع الآن **706 اختبارًا** يمر.

### تريد التراجع؟

لا حاجة لأي تراجع: **لا شيء في هذه المرحلة يعمل تلقائيًا**. حتى لو نفّذت الخطوات
كاملة، فالسلوك الافتراضي هو الحجب. لو أردت العكس صراحةً:

```bash
export SUPABASE_INCLUDE_CLINICAL=1     # ضمّ قسم followups (لا يُنصح به)
export SUPABASE_EXCLUDED_SECTIONS=followups,voice   # توسيع الاستثناء
```

## 5) حدود معروفة (بصراحة)

- **الأسماء المجرّدة**: فحص النصوص يلتقط «المريض + اسم» ورمز `P-1xx`، لكنه لا
  يكتشف اسم مريض مكتوبًا وحده بلا سياق («أحمد يحتاج موعد»). لا يوجد في المستودع
  نموذج تمييز أسماء (NER)، وإضافته قرار منفصل.
- **الإفراغ يُفقد الاستعادة السريرية**: بعد الاستعادة من السحابة سيكون قسم
  `followups` فارغًا — لأن نسخته السحابية لا تحمل مرضى عن قصد. الصفوف الستة تبقى
  كما هي في `data/state.json` المحلي (الفلتر لا يمسّ الحالة المحلية) وفي
  `data/master-sheet.xlsx` في Git.
- **الترحيل لمرة واحدة**: `engine/migrate.py` ليس مزامنة ثنائية الاتجاه. بعد
  الترحيل، المصدر هو `state.json` (قاعدة الكاتب الواحد).
- **النسخ لا تُلغِ الحد المجاني**: خطة Render المجانية بلا قرص دائم؛ النسخة
  السحابية هي الذاكرة، لذا التوقيت مهم عند الإيقاف اليدوي.

## 6) جدول الرايات

| الراية | الافتراضي | الأثر |
|---|---|---|
| `AI_OS_STATE_RESTORE_ON_BOOT` | معطّلة | استعادة آخر نسخة عند الإقلاع |
| `AI_OS_STATE_PERSIST` | معطّلة | دفع تفاضلي دوري |
| `AI_OS_STATE_PERSIST_SECONDS` | 120 | دور الدفع |
| `AI_OS_STATE_RESTORE_FORCE` | معطّلة | استعادة قسرية فوق حالة محلية |
| `SUPABASE_EXCLUDED_SECTIONS` | `followups` | أقسام لا تُرفع أبدًا |
| `SUPABASE_INCLUDE_CLINICAL` | معطّلة | ضمّ `followups` صراحةً (غير موصى به) |
| `SUPABASE_WRITE_ENABLED` | معطّلة | السماح بأي كتابة في Supabase |
| `AI_OS_DATA_DIR` | `data/` | مجلد الحالة (يُستخدم للترحيل في مجلد منفصل) |
